# 从有效记录到持久化检查点覆盖

2026-11-15。本轮收紧恢复诊断的通过条件：此前新增记录合法、双向对应即可 verified，但新增数据尚未进入持久化检查点，其后丢失不一定可检测。现在这类状态独立返回 `uncheckpointed`（退出码 6），提醒显式推进检查点。

## 判定与兼容性

完整双向扫描后，在同一源库快照内，将索引数和证据数分别与已验证检查点的计数相减，输出 `uncheckpointed_counts`，分别包含 `intents`、`records`。旧历史已验证，因此多出的记录代表尚未纳入该检查点的追加部分。未扫描完整时该字段为 null，不用部分计数推测全库。

状态优先级：已见异常 blocked（5）→ 扫描不完整 incomplete（4）→ 未落账 pending（3）→ 有效但未覆盖 uncheckpointed（6）→ 全部有效且覆盖 verified（0）。这是 CLI 行为变更：消费退出码的调用方必须处理新增的 6，不能将所有非零返回都当成数据库损坏。

诊断仍然只读，不自动发布检查点。操作方应在核查后使用 `CheckpointStore.advance(..., expected_generation=报告中的版本)` 显式推进，再重新诊断；期间如果其他发布者已更新，将由版本比较拒绝过期请求。后续又有追加，重新诊断仍可能返回 6，不能把一次推进当作永久覆盖。

## 完整流程实验

```sh
make checkpoint-coverage-check CHECKPOINT_COVERAGE_OUTPUT=outputs/evaluations/checkpoint-coverage-new
```

使用合成审计 receipt、虚拟证据时钟、真实 SQLite 和独立 CLI 子进程：

1. 写入第一条记录并登记 generation=1，保存旧备份；追加第二条记录。诊断返回 6，明确索引和证据各有 1 条未覆盖。
2. 显式推进 generation=2。重新诊断返回 0，未覆盖计数均为 0。
3. 仅将源库恢复为第一步旧备份，保留 generation=2 仓库。诊断返回 5，原因 history_mismatch。

3/3 阶段符合预期；每次诊断前后输入文件哈希不变，并分别保存每个阶段的数据库和仓库副本。[运行记录](evaluations/checkpoint-coverage-v1.json)包含全部结果、源代码及阶段副本哈希。69 项证据链测试和 12 项仓库测试通过，共 81 项相关测试；新增 3 项测试覆盖显式推进、部分扫描未知覆盖和 pending 优先级，并更新旧新增记录测试的预期退出码。

这一步把“发现有效记录”与“已具备检查点回退检测依据”变成可区分的操作状态，并验证了显式推进后的检测闭环。覆盖仅相对于本次观察到的仓库版本和源库快照；源库与仓库一起回退、检查点自身丢失、两库之间并发变化仍受原有限制约束。它不是跨库原子提交、数据备份或机器人动作授权，也没有实机与断电保证。
