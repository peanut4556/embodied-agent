# 多进程检查点竞争与锁持有者退出

2026-11-15。本轮将上一轮检查点仓库的串行故障验证拓展到真实多进程竞争。新增可重复执行的进程编排脚本，默认仓库实现未改动。

## 实验设计

每组使用独立数据库和仓库，先写入一条合成证据并登记 generation=1，再追加第二条证据。串行预热三个 spawn 进程，使初始化竞争与发布竞争分开；主进程通过管道下发命令，响应等待有上限，结束时验证所有工作进程退出。

两种场景各运行三次：

- **三个发布者竞争**：向三个进程发送相同 expected_generation=1，允许调度自然重叠。要求恰好一个 `published`，其他返回锁竞争的不确定结果或 `generation_conflict`；最终 generation=2，检查点覆盖两条记录。随后向存活进程再次提交旧版本，必须拒绝。
- **锁持有者退出**：第一个进程持有 BEGIN IMMEDIATE 写锁，第二个进程发布失败并报告 `publication_unconfirmed`；第一个进程以 `os._exit(83)` 退出。主进程先读取并确认 generation 仍为 1，再显式指示第三个进程发布，成功推进到 2。旧版本请求仍必须拒绝。

这是显式实验调度，不是生产自动重试机制。锁竞争本身不能证明提交结果；先核对仓库的步骤保留。持锁退出场景未写入新行，提交途中崩溃仍由上一轮实验覆盖。

## 结果与复现

```sh
make checkpoint-contention-check CHECKPOINT_CONTENTION_OUTPUT=outputs/evaluations/checkpoint-contention-new
```

6/6 组实验通过，18 个工作进程全部退出回收；原有 12 项仓库单元测试回归通过，Ruff 检查通过。[实验摘要](evaluations/checkpoint-contention-v1.json)包含所有发布结果、最终检查点，以及源代码、完整报告、数据库和仓库哈希。

新增能力是可运行的多进程故障验证工具：从串行更新测试推进到实际并发发布与锁所有者退出后的恢复。使用真实 OS 进程、SQLite 文件和 IPC；证据输入是合成数据，证据时钟是虚拟时钟。没有接入实机，没有测得吞吐或公平性保证；有限次数的竞争测试不构成所有调度路径的形式化证明。三个命令并不保证在同一 CPU 时刻执行，锁持有者场景则明确保证第二个进程发布时锁仍被占用。

本轮未增加远端见证、自动重试或机器人动作授权。源库与仓库同时回退的限制仍然存在。后续若优化发布并发性能，可以直接复用此脚本检查“同一版本至多一次成功更新”和进程退出后的锁恢复行为。
