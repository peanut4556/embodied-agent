# 从真实进程采集到检查点发布的完整联调

2026-11-15。本轮将最近的存储、提案和恢复能力接回已有采集链，新增一键联调脚本。它不手工构造已确认 receipt，而是通过真实工作进程执行预约采集、两阶段确认及一次性领取，再将实际产生的证据交给账本。

## 完整路径

1. 初始化 CheckpointedEvidenceLedger，独立仓库显式登记空基线。这些磁盘初始化在短时证据产生前完成。
2. CaptureRecovery 使用 reserved 配置启动真实 spawn 采集进程，执行 31 次候选采集和 5 次新鲜见证。
3. EvidenceInbox 从活的 handoff 领取证据，派发时复核期限；消费者使用默认实际 monotonic 时钟落账。记录接收时间距离原始到期时间的余量。
4. 回收采集进程后，依次启动独立 CLI 进程：发布前审计、预览、从提案文件发布、发布后审计、按提案查询发布记录。
5. 核对只消费一次、检查点覆盖状态变化、发布结果以及资源退出。完整报告保留 manager 状态；摘要包含各阶段结果和文件哈希。

短时门槛只用于接收新鲜证据；后续提案和发布处理历史审计数据，不给证据续期，不产生机器人动作授权。

## 实验结果

```sh
make capture-publication-check CAPTURE_PUBLICATION_OUTPUT=outputs/evaluations/capture-publication-new
```

首轮 4/4 符合预期，四次均完成 36 个请求并得到 confirmed_recent_evidence：

| 模式 | 次数 | 消费与存储 | 后续链路 |
| --- | --- | --- | --- |
| 立即派发 | 2 | 各消费一次、成功落账 | 审计 6 → 预览 0 → 发布 0 → 审计 0 → 发布对账 0 |
| 入队后等待 30 ms | 2 | expired_in_queue，消费者零调用 | 不生成提案、不发布 |

两次立即路径的账本接收时间距离原始到期时间约 6.26 ms、6.78 ms。该值是接收时刻余量，不是磁盘提交结束余量；不能据此声称 fsync 总在期限内完成。所有重复派发都返回 no_pending_evidence，所有采集工作进程已回收。

[实验摘要](evaluations/capture-publication-v1.json)保存源文件哈希、原始报告位置/哈希、数据库/仓库哈希、交付结果和 CLI 输出。102 项相关证据、仓库、发布及命令测试回归通过，新增脚本 Ruff 检查通过。

## 能力与限制

进展是把此前分别验证的组件接成实际运行流程，证明在这轮真实时钟调度中，新鲜证据可以进入持久化、审核提案及发布对账；过期证据则在入口被截断。读取器仍是合成双视角数据，没有真实相机、头显或机器人。四次实验不代表长期成功率，也没有增加实时调度保证。

脚本保留所有运行结果；若未来采集迟到、落账超时或 CLI 失败，写出报告后以非零状态退出，不自动重采或挑选成功结果。预览到发布由实验脚本显式调用，没有模拟真人审批或身份认证。持久化回执丢失与崩溃对账仍由前轮故障实验覆盖，本轮不声称在完整采集链上又验证了一遍所有崩溃点。
