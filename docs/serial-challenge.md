# 单请求采集控制器与因果时序验证

本轮把“固定曝光序列加交付延迟”的回放扩展为有请求生命周期的控制器。`SerialChallengeController` 先发请求，驱动返回后才可能发下一请求，拍摄时间必须属于该请求区间。新增渲染实验在实际发出的虚拟请求时刻生成新 RGB-D，不用旧图像插值或补齐曝光。

这里的“实际请求”指控制器在确定性虚拟时钟中的请求事件，**不是硬件相机请求或实测渲染耗时**。本轮仍未接入真实相机、WebSocket 或 Zenoh。

## 可接入的接口

```python
control = SerialChallengeController(
    start, clock_map, session_id,
    position_error_m=budget, delivery_budget_s=0.1,
)
request = control.poll(task_now, host_now)
# request 非空时，由调用者发起一次独占的双视角采集。
# 结果回来后使用原 request_id 和真实曝光时间提交：
control.complete(request.request_id, task_now, host_now,
                 primary_stamped, secondary_stamped,
                 session_id=request.session_id)
```

- `poll` 非阻塞，只返回采集请求描述，不自行启动线程或访问设备。
- 同一时刻最多一个请求在途；结果未返回时重复 poll 不会发出新请求。
- 请求包含编号、会话、任务时间和主机时间；两路曝光都必须在请求发起之后、结果返回之前。
- 旧请求编号、重复回调、终态后的迟到结果不增加证据，也不能完成新请求。
- 当前请求默认 250 ms 超时，卡住后终止，不把仍可能运行的驱动调用当作已结束后再发一个。
- 无结果期间也检查任务/主机时钟映射；停止立即锁定取消状态。
- 原三秒曝光期限、显式 100 ms 交付预算、最多 31 次请求及全部复核规则保留。
- 终态但仍有在途请求时 `driver_cancel_required=true`；驱动取消和资源回收仍由调用方负责。该标记不证明原驱动已经停止。

顶层 status 是控制器结论，内部 confirmation 快照保留证据状态。时钟倒退抛出调用错误，不修改此前状态。截止时刻有结果时应先 complete 再 poll；零延迟理论对照允许在三秒边界发最后请求并立即交付，再次 poll 未收到结果则关闭窗口。

## 新渲染协议

三种场景：静止、0.4 秒时 2 N/20 ms 脉冲后恢复、200 ms 周期/10 ms 相位的 1.2 N/20 ms 扰动。保持既有物理场景、摩擦、质量与 2 ms 步长。两个新深度噪声种子，每种场景运行五种服务条件，共 **30 条运行**。

服务条件为 20、50、80、100 ms，以及第一次高频复核请求永久不返回。模型假定每次请求立即曝光，然后占用驱动直到指定处理延迟结束；处理延迟由虚拟时钟注入，不是图像渲染实测耗时。完成事件优先处理，然后才允许新的请求。任何请求重叠都会使实验报错。

场景按物理步持续积分。只在控制器发请求时采集新 RGB-D，整个深度图加入标准差 1 mm 噪声；共同采样时刻按 `(种子, 场景, 物理步)` 派生相同噪声。真值只记录与评分，不传入复核器。确认后的交付时刻也记录物体真实位置。

## 结果

两个噪声种子一致。每种服务条件包含 4 个静止/恢复案例和 2 个周期扰动案例。

| 服务条件 | 静止/恢复确认 | 周期扰动确认 | 单例采集请求与原因 |
| --- | ---: | ---: | --- |
| 20 ms | 4/4 | 0/2 | 静止/恢复 31 次；周期运动 12 次后拒绝 |
| 50 ms | 4/4 | 0/2 | 静止/恢复 31 次；周期运动 12 次后拒绝 |
| 80 ms | 0/4 | 0/2 | 各 12 次，复核曝光间隔超限 |
| 100 ms | 0/4 | 0/2 | 各 12 次，复核曝光间隔超限 |
| 首个高频请求卡住 | 0/4 | 0/2 | 各 12 次，请求超时，要求取消驱动 |

20 ms 和 50 ms 的成功结果分别在 3.02、3.05 秒交付，最后曝光仍在三秒内。全部确认时目标在保守区域内。周期扰动在这两个条件下被原始范围复核发现；80/100 ms 下是时序拒绝，不能计为运动检测能力提升。

以静止 80 ms 为例：候选图像在 2.00 秒拍摄，2.08 秒返回；控制器此时才知道要开始高频复核，下一请求最早 2.08 秒，不能回到 2.05 秒补拍。两次曝光间隔达到 80 ms，超过 60 ms 连续性限制，2.16 秒收到结果后拒绝。

这解释了与上一轮结果的差异：[交付预算实验](delivery-budget.md)按预先存在的 20 Hz 图像回放，80/100 ms 延迟可以在 3.1 秒内交付，但没有证明这些图像能由串行请求产生。本轮增加因果请求约束后，暴露了这个可用性缺口。两轮结论分别针对不同采集模型，并不矛盾。

50 ms 刚好等于高频间隔，没有额外调度开销余量；本轮不证明在 OS 抖动、真实相机同步、网络和编码开销下仍能通过。也没有通过缩短稳定窗口来挽回高延迟确认。

## 验证与复现

```sh
make serial-challenge-test
make serial-challenge-evaluate SERIAL_CHALLENGE_OUTPUT=outputs/evaluations/serial-challenge-new
```

[实验摘要](evaluations/serial-challenge-v1.json)保存每例状态、请求数、确认时刻、取消需求、源文件哈希和完整报告路径与 SHA256。完整报告包含请求、返回、每次曝光对应的 RGB-D 检测和状态真值；不保存原始图像或逐物理步全部真值。输出目录独占创建，失败保留报告。

新增 10 项测试覆盖串行因果性、零延迟边界、高延迟无法伪造 20 Hz、在途去重与超时、缓存帧、未知/重复回调、等待期间时钟漂移、停止、采集期限、会话/缺失及快照与时间倒退。连同原交付、复核、曝光、采集和核心回归共 **109 项通过**，Ruff 检查通过。图形驱动仍提示 ARB_clip_control 不可用。

下一步若需要支持更慢处理，应明确选择连续曝光缓冲、流水线处理或不同观测协议，并验证其帧龄、占用上限与取消行为；不能仅增加返回期限就宣称满足原高频采样要求。默认执行端未切换到本模块。
