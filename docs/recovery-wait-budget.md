# 跨恢复代的等待预算分配

日期：2026-11-18。

本轮将读取器的 CPU 预算回退接入 `CaptureRecovery`，并验证独立监督超时后的完整新会话确认。关键变化是每次新建读取器不再领取整个配置阈值，而只能领取预先划定的代际份额。

## 分配合同

新增可选 `wait_cpu_budget_s`，仅允许 reserved 模式，默认 `None`。有限范围沿用读取器的 0–1 秒校验；配置 0 时各代都直接休眠。总阈值按 `max_generations` 均分，在调用采集后端构造器之前记录代数、会话编号、份额。浮点剩余额度保护确保不会因尾数误差分配超出剩余值。

- 启动失败、构造异常、任务失败、主动停止均不退款，不根据缺失遥测推测未使用额度。
- 清理未确认时不开始下一代、不分配份额；构造异常仍锁定为所有权不确定，禁止继续恢复。
- 配置预算时自动开启等待计时与进程遥测。每代读取器使用其分配阈值，耗尽后后续请求停用自旋。
- `result().wait_cpu_budget` 报告总阈值、分配策略、每代份额和未分配余额；快照不允许通过返回值修改内部记录。
- 默认未配置预算时维持旧行为；仍要求显式启动新代，不自动重放任务。

例如总阈值 10 ms、最多两代，每代只有 5 ms；第一代即使初始化失败，第二代也不会取得第一代的 5 ms。代数上限既限制重建次数，也限制份额分配次数。

这是一种保守分配策略，可能浪费启动失败代的份额。总阈值是各代触发回退阈值之和，不是总线程 CPU 上限：当前请求可能越过阈值，休眠仍有成本，初始化、读取器和其他线程成本不计入。管理器结果显式标注 `hard_cpu_limit: false`。新建整个管理器会重新配置预算，没有跨管理器持久化或全局资源管控。

## 两次固定联调

实验前保存计划和源码摘要，两次运行都配置：两代、总阈值 10 ms、末段自旋 1.5 ms、独立监督作业时限 4 s。第一代工厂永久阻塞并忽略 SIGTERM；监督回收后显式启动合成读取器。完整执行候选与见证确认，再立即消费新证据、检查重复消费拒绝和第三代启动拒绝。失败记录会保留，不为获得成功重跑。

| 项目 | 第一次 | 第二次 |
|---|---|---|
| 第一代超时与退出核验 | 通过 | 通过 |
| 分配记录 | 5 ms + 5 ms，无退款 | 5 ms + 5 ms，无退款 |
| 第二代请求数 | 36 | 36 |
| 回退休眠请求 | 5–36 | 5–36 |
| 第二代等待 CPU 总量 | 13.273 ms | 12.257 ms |
| 完整确认及首次消费 | 通过 | 通过 |
| 旧会话／重复消费／第三代拒绝 | 通过 | 通过 |

两次均达到 `confirmed_recent_evidence`，证据分别剩余约 11.23 ms、12.44 ms 有效期时消费。各代进程回收确认。报告将预算与清理核验、完整恢复通过分开记录；命令退出码只表示预算与清理核验是否通过，完整恢复结果需读取 `full_recovery_passed`，不会把任务失败改记成功。

本轮没有无预算对照，不能据此比较成功率或 CPU 改善，也不能与前几轮错窗结果作因果比较。实际 OS 进程与单调时钟，位置数据仍是合成；没有真实驱动、相机、机器人验证。消费证据不授权机器人动作。
