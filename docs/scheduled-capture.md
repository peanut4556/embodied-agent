# 提前预约曝光：把派发延迟移出曝光窗口

2026-11-13。接续[采集时间链诊断](capture-timing.md)，新增独立的预约式读取适配器，并以真实进程/真实时钟比较到点派发与提前派发。所有位置均由合成读取器生成，没有真实相机，也没有执行抓放或任务确认。

## 新增协议

`ScheduledPairRequest` 分开记录实际预约创建时间 `host_time`、目标曝光时间 `target_host_time`、最晚曝光时间 `latest_host_time`，不把目标时刻冒充实际请求时间。提前量限于 0–250 ms，曝光窗口限于 0–10 ms，请求编号限于 1–36，会话必须非空且有界。

`ScheduledReaderFactory(factory)` 在工作进程中创建底层读取器并包装为 `ScheduledPairReader`。适配器最多按 1 ms 间隔 sleep，等待目标时刻，不忙等。如果唤醒时已经过期，直接拒绝，不补拍、不平移窗口。读取后核验两路实际曝光时间均在窗口内、未早于本次读取开始、未晚于返回时间，并检查会话一致。读取器返回较慢不会把曝光时间改成返回时间；帧的新鲜度需要上层另行验证。

适配器复用已有 `ProcessPairCapture` 的预热、双进程容量、每会话最多 36 个请求、取消和强制回收机制。等待期间占用一个工作进程；读取本身卡死仍由进程所有者取消，不通过重试积累更多工作。

```python
backend = ProcessPairCapture(ScheduledReaderFactory(camera_factory), trace_timing=True)
try:
    if backend.wait_ready():
        issued = time.monotonic()
        request = ScheduledPairRequest(1, session_id, issued, issued + 0.020, issued + 0.022)
        accepted = backend.submit(request)
        # 调用方轮询 drain，处理失败并核验新鲜度；accepted 不表示曝光或任务成功。
finally:
    backend.cancel()
    cleanup = backend.reap(0.25)
```

## 对照实验

固定目标时刻序列：从既有相位扫描的前 11 个间隔取 10 个 52 ms 和 1 个 58 ms，形成 12 个曝光窗口。每窗口仍严格为目标之后 2 ms；未改宽窗口。

- 到点模式：主循环到目标时刻再提交，工作进程立即调用合成读取器。
- 预约模式：提前 20 ms 提交，由工作进程到目标时刻再调用同一合成读取器。
- 四种条件：正常、派发前等待 5 ms、读取器曝光前等待 5 ms、曝光后返回前等待 5 ms。
- 每个组合运行 3 次，每次 12 个窗口，共 24 次运行、288 个窗口；第二轮交换两种模式的执行先后。
- 不并发运行本项目测试来干扰测量，但没有进行操作系统负载隔离或实时优先级配置。缺失、过期、未提交、容量不足都计为未满足窗口。

| 条件 | 到点派发满足窗口 | 提前预约满足窗口 |
| --- | ---: | ---: |
| 正常 | 35/36 | 35/36 |
| 派发前等待 5 ms | 0/36 | **36/36** |
| 读取器曝光前等待 5 ms | 0/36 | 0/36 |
| 曝光后等待 5 ms | 36/36 | 36/36 |

派发延迟条件下，预约模式三次均为 12/12，到点模式三次均为 0/12。这提供了一个具体机制的实验支持：预留的 20 ms 可以吸收本次注入的派发等待及实际 IPC 延迟，避免将它们全部压进 2 ms 曝光窗口。

**提前预约没有消除所有时序失败。** 正常条件下到点模式一次曝光晚约 2.095 ms；预约模式一次工作进程过晚唤醒，按 `scheduled_capture_window_missed` 拒绝。读取器自身曝光前的 5 ms 等待也无法被该包装器吸收，因为包装器只在目标时刻才调用读取器。支持真正的硬件定时触发或提前准备，需要另一个设备契约。

24 次运行均核实工作进程退出。合成实验继续执行后续窗口只是为了收集独立槽位的诊断数据，不是失败后自动继续机器人任务；整份报告明确标记 `task_confirmation_performed=false`。

## 边界与接入要求

本轮是采集协议原型及对照实验，尚未接入现有 `TwoStageCaptureController`、`CaptureRecovery` 或默认执行路径。原两阶段控制器只允许到点创建请求，不能简单提前调用 `poll`，也不能把旧帧当新请求结果提交。未来接入必须显式处理预约生命周期、超时起点、候选到见证切换、实际曝光时间与取消隔离。

288 个窗口不是 288 个抓放任务，也不是长期成功率估计。统计只判断两路曝光是否落在计划窗口，不判断空间正确性、持续静止、新鲜见证或动作安全。实验固定位置和短序列也没有解决之前记录的窄脉冲感知盲区。

原来的 `analyze_capture_timing` 假设到点才创建请求，不适用于预约式请求；本实验保留原始进程时间追踪，直接按目标窗口核验曝光，不把合法的提前请求强行塞入旧分段公式。
