# 跨应用进程的持久化预算恢复

日期：2026-11-19。

本轮新增三阶段独立应用进程联调，把持久化份额分配、初始化失败回收、预约采集、自旋回退、近期证据交付及耗尽拒绝接成可重复验证的流程。没有修改生产默认配置。

## 固定计划与重启条件

预先保存两轮实验计划和源码摘要。每轮创建独立预算数据库，总回退阈值 10 ms、两个槽位，每份 5 ms。依次执行三个独立 Python 应用进程，各自重新创建恢复管理器并打开同一数据库：

1. **失败应用**领取第一份额度，读取器初始化永久阻塞并忽略 SIGTERM。独立监督在 4 s 作业时限后终止并回收。应用保存清理记录后 `os._exit(74)`。
2. **恢复应用**在外部编排器核验上一进程退出码、超时记录、清理确认和已分配槽位后才能启动。新应用只领取第二份额度，运行完整候选/见证采集，消费近期证据一次，再检查重复消费拒绝。旧会话尝试也必须拒绝。
3. **耗尽应用**再次打开同一数据库并启动任务，必须因持久化额度耗尽拒绝，且 `backend_created` 为 false。

每个应用启动都有外部 20 s 超时，内部采集作业仍由独立监督限制。源码摘要在结束时复核；每阶段 JSON 和日志落盘，失败不重跑。第一阶段清理不通过时停止，不继续接管。阶段报告损坏、缺失或进程异常会使编排失败，已产生的文件保留。

这模拟应用退出后的重新启动，但失败应用退出前已确认采集作业回收；不是任意时刻杀死主程序后的设备所有权恢复，也没有在数据库分配和硬件动作之间建立分布式事务。

## 本轮结果

| 项目 | 第一轮 | 第二轮 |
|---|---|---|
| 三个应用退出码 | 74 / 0 / 0 | 74 / 0 / 0 |
| 第一份额度在新应用中仍已消耗 | 通过 | 通过 |
| 第二应用完整请求数 | 36 | 36 |
| 回退休眠请求编号 | 5–36 | 5–36 |
| 第二应用等待 CPU 总量 | 11.818 ms | 12.235 ms |
| 完整确认与首次证据消费 | 通过 | 通过 |
| 旧会话与重复消费拒绝 | 通过 | 通过 |
| 第三应用启动前耗尽拒绝 | 通过 | 通过 |

两次均达到 `confirmed_recent_evidence`。证据消费时剩余有效期分别约 16.48 ms、8.59 ms，始终不授权机器人动作。预算池最终都分配两个槽位，剩余阈值为 0。实际等待 CPU 大于阈值是预期行为：阈值只决定后续请求是否停用自旋，休眠与跨阈值的当前请求仍有成本。

`integrity_verified` 单独报告池身份、份额、清理、逐请求回退轨迹及耗尽拒绝是否一致；`full_recovery_passed` 还要求完整 36 请求确认及一次性消费。命令退出码核验前者，完整任务结果必须查看后者，不能用实验命令成功替代任务成功。两轮两者均为 true。

## 验证及限制

59 项相关测试通过。新增 4 项覆盖完整确认与结构正确的区分、未确认清理时阻止重启、池身份/槽位复用/拒绝时仍启动后端的拒绝判定、错误回退与缺失遥测的拒绝判定。既有持久化预算、恢复、预约时序和监督回归通过。Ruff 与源码/阶段报告哈希校验通过。

```sh
make persistent-recovery-check PERSISTENT_RECOVERY_OUTPUT=outputs/evaluations/persistent-recovery-new
make persistent-recovery-test
```

使用实际 OS 进程、SQLite、IPC 和时钟，但位置数据仍是合成读取器。仅两次短时实验，没有无预算对照，不支持成功率提升或 CPU 节省的因果结论。没有真实相机、机器人、掉电、数据库回滚或设备租约验证。

[提交摘要](evaluations/persistent-recovery-v1.json)包含两轮结果、源码哈希和六份阶段报告哈希；原始报告、日志、数据库及计划在本地忽略目录 `outputs/evaluations/persistent-recovery-v1/`。下一步若推进设备接管，需要单独定义旧作业所有权的外部确认条件，不能把预算池当作设备锁。
