# 预约等待的 CPU 成本与目标迟到测量

2026-11-16。本轮新增工作进程内的可选等待遥测，回答末段自旋是否值得采用。观测真实线程 CPU 时间、等待墙钟时间和唤醒目标迟到，成功和失败路径均通过已有 IPC timing_trace 返回。

```python
manager = CaptureRecovery(
    position_error_m=(0.001,)*3, capture_profile='reserved',
    supervised=True, runtime_limit_s=4, spin_window_s=0.0015,
    trace_timing=True,
)
```

预约读取器可单独设置 measure_wait=True；默认关闭。每个请求记录 request_id、wait_elapsed_s、wait_cpu_s（thread_time 差值）、sleep_calls、spin_iterations、target_lateness_s 和 window_missed。每次请求开始清除旧指标，时钟异常不会沿用上一请求数据。后端最多保留原有 36 个请求的 trace，不引入无限历史。

CPU 时间仅覆盖执行等待循环的线程，不是整个采集进程树 CPU 或能耗；目标迟到量取等待结束时刻与目标时刻之差，不是实际相机曝光误差。真实曝光戳仍由原合同独立检查。测量与传输有额外开销，不能将结果视作完全无扰动的基准。

休眠合计 38 个请求，平均等待 CPU 约 0.203 ms/请求；自旋合计 12 个请求，约 1.368 ms/请求，约为前者 6.7 倍。不同运行提前终止的位置不同，观测请求分布也不同，这不是匹配的完整任务 CPU 对照，更不是统计显著的可靠性比较。

本轮结论：测到了自旋成本，未测到可靠性改善。上一轮同样顺序四次全通过，本轮四次全拒绝，再次说明少量不同时间的调度实验不能用来宣称已解决问题。测量开销、系统负载和调度波动尚不能从现有样本中分离。保留默认关闭，不调整 2 ms 曝光门槛。

[实验摘要](evaluations/wait-cost-v1.json)包含所有统计、源码哈希和完整逐请求报告位置/哈希。3 项新增测试验证测量、失效清除、失败指标跨进程传输和配置；原预约读取器 11 项、进程后端 9 项、恢复管理器 9 项、自旋 3 项回归通过，共 35 项相关测试。Ruff 检查通过。

新增能力是可观测的成本—时序诊断，不是性能提升承诺。实验读取器仍为合成双视角、时钟与进程为真实运行，没有实机和功耗结论。后续需要更长时间、多批次、固定请求分布及明确负载条件的测量。
