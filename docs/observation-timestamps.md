# 带采集时间戳的观测契约

2026-10-27。为 ObservationCapture 增加 StampedPosition 和显式 require_timestamp=True 严格模式，解决“请求刚完成，但返回的其实是缓存旧帧”无法仅靠请求耗时识别的问题。原坐标列表接口默认继续兼容。

## 驱动契约

```python
StampedPosition(position=(x, y, z), captured_at=exposure_monotonic_time)
```

captured_at 必须是曝光/采集时刻，已由驱动映射到适配器使用的本机单调时钟域。不能直接填写 Unix 时间、设备原始计数或任务/模拟时间，也不能用“收到结果时的当前时间”给旧帧重新盖章。

适配器验证时间戳有限且满足“本次请求开始 ≤ 采集时刻 ≤ 驱动返回时刻”。因此请求前曝光的缓存帧，即使快速返回，也会被拒绝。未来、NaN、Infinity 时间戳同样转换为缺失观测，并保留错误原因。None 仍表示没有有效观测，不要求附加时间戳。

严格模式拒绝无时间戳的坐标列表。兼容模式仍接受旧接口，但采集时间和数据年龄标为 None，不假装已验证曝光新鲜度。即使在兼容模式，显式提交的 StampedPosition 也必须通过时间检查。

原 250 ms 请求到消费的年龄上限、单次消费、超时隔离、取消与单在途约束保持不变。有效结果在工作线程中转换为独立坐标副本，防止驱动随后修改缓冲区。时间戳异常不能把已经构造的位置泄漏给确认器。

## 可审计的双时钟记录

CapturedReleaseObserver 新增 capture_records，与每次实际观测调用对应，记录 task_time、captured_at、age_seconds、capture_status 和 error。任务时间仍用于确认预算；采集年龄在单调时钟域内计算，两种时间不会直接相减。

例如测试中任务时间为 0.2 秒时消费了单调时钟 10.0 秒采集的位置，数据年龄为 0.2 秒。记录保留这两个时刻，而不是把采集时间伪装成任务时间。每次消费和取消都会清除旧采集元数据，预取下一帧不会覆盖已经保存的记录。

确认器目前仍以消费时的任务时间计算稳定区间；本轮增加的是时间来源契约、新鲜度拒绝与可审计记录，尚未实现基于曝光时间重建运动速度。设备时钟同步、映射漂移和驱动时间戳真实性仍由驱动及后续校准验证，适配器无法自行证明。

## 验证

新增 5 项测试覆盖有效时间戳及坐标拷贝、缓存旧帧/未来/非法时间拒绝、严格与兼容模式、无观测，以及完整观测包装层的双时钟记录和连续确认。共 124 项测试通过（58 核心、31 接触、22 释放相关、13 采集适配）；Ruff 与 diff 检查通过。

测试使用真实工作线程和可控时钟，没有连接真实相机，也没有新物理实验。默认生产路径未启用严格采集；本轮没有宣称设备时钟已校准或动态场景误确认问题已解决。

## 使用

```python
capture = ObservationCapture(driver_read, require_timestamp=True)
observer = CapturedReleaseObserver(capture, allow_recheck=True)
```

driver_read(cancel_event) 返回 StampedPosition 或 None。驱动需独立拥有相机资源，不能共享未经同步的模拟渲染器。已有不带时间戳的驱动可继续使用默认兼容模式，但不具备缓存帧拒绝保证。

复现测试：`make observation-capture-test`。下一步可用独立相机桩注入时钟漂移和动态物体，检验曝光时刻与任务时间的映射，再决定如何让确认器使用曝光间隔。

后续新增[双时钟确认原型](exposure-confirmation.md)，通过合成位置序列验证曝光间隔与送达间隔的差异；尚未接入完整采集流水线。
