# 有界流水线曝光调度

2026-11-10。本轮实现实验性 `PipelinedChallengeController`，用于检验单请求控制器暴露出的因果采样瓶颈。未接入默认执行端，未启动相机线程，也未训练或应用新校正。

## 协议与实现

控制器在任务开始时固定 31 个请求时刻：0–2 秒每 200 ms 一次，2.05–3 秒每 50 ms 一次。后段提前安排，不等待 2 秒候选的处理结果；因此可以在候选结果返回前拍下 2.05 秒的新图像。仍由原 `DeliveredChallenge` 和 `ConfirmationChallenge` 判定稳定、跨视角一致性、原始运动范围、帧龄与期限，不预先假定候选成立。

- 默认最多两个在途请求，容量可显式设为 1–31。达到计划时刻却没有空位，立即 `pipeline_capacity_exhausted`，不排无限队列、不补拍。
- 本版要求请求准时且立即成对曝光（仅 1 ns 数值容差），曝光时间等于请求的主机时间。错过时刻即 `capture_schedule_missed`。这是确定性协议原型，不是容忍操作系统抖动的真实驱动。
- 回调必须按请求顺序交付。已知请求乱序即终止，不通过重排或伪造交付时间挽救结果。未知、重复和终态后的回调隔离计数。
- 独立检查每个请求的 250 ms 超时；原曝光帧龄上限仍生效。曝光截止三秒，实验显式允许额外 100 ms 返回时间。同一时刻先交付，再 poll。
- 取消、超时、拥塞或证据失败后输出仍在途的 `cancel_request_ids`，调用方负责停止驱动并回收资源。该列表不表示取消已完成；本模块不拥有硬件或线程。
- 固定后段适用于最早两秒候选路径。候选更晚、不成立或观测异常时，可能因证据时间不符合原规则而拒绝；没有放松原稳定窗口来提高通过率。

请求与事件记录最多各 31 条；内存中保存的是请求元数据，不是 RGB-D 图像。真实系统还需要对图像缓冲字节数、工作线程和驱动资源单独限额。两个在途请求要求驱动具备流水线处理或并行工作能力；单个耗时 80 ms 的串行处理器不会因为有两个缓存槽就获得 20 Hz 吞吐量。

## 确定性时序实验

30 个合成案例：五种固定处理延迟 × 三种容量 × 静止/位移两种输入。虚拟时间步长 1 ms，请求时立即生成带曝光时间的坐标，随后才允许返回。静止坐标 `(0.64, 0, 0.045)`；位移案例从 2.05 秒起 x 增加 2 mm。误差预算固定每轴 1 mm。这些坐标不是新 RGB-D 检测或物理仿真结果。

| 固定处理延迟 | 容量 1：静止确认 | 容量 2：静止确认 | 容量 3：静止确认 |
| --- | --- | --- | --- |
| 20 ms | 是 | 是 | 是 |
| 50 ms | 是 | 是 | 是 |
| 80 ms | 否，容量不足 | 是 | 是 |
| 100 ms | 否，容量不足 | 是 | 是 |
| 120 ms | 否，容量不足 | 否，容量不足 | 否，交付期限到达 |

所有通过案例均为 31 次请求，最后曝光在 3 秒，返回在 `3 秒 + 处理延迟`；在途峰值不超过配置容量。15 个位移输入均未确认，其中容量足够的案例由原运动门槛拒绝，其余属于调度拒绝，不能视作运动检测成功。80/100 ms、容量 2 的结果说明提前安排曝光和两个在途槽可以解除理想固定延迟下的串行瓶颈；不证明真实相机、网络或多线程吞吐已达标。120 ms 即使增加容量，也不能越过 100 ms 的返回预算。

本轮没有随机抖动、长期统计、真实图像或设备验证。下一步可用新的物理渲染样本检验该协议，并在明确同步和抖动容差后再对接驱动。
